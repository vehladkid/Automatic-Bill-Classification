## 2. Near-duplicate investigation (the 116 / 161 finding)

**Cause: shared layouts (templates), not repeated documents, not shared issuers, and partly an audit limitation.** In v2 the generated split grouped by *issuer*, but every generated document has its own issuer, so `group_id` was effectively per document and could not protect against template reuse. All 3 seen layouts (A/B/C) of a document type were present in train, val and test; 100% of the seen-layout val/test pages therefore had a same-type, same-layout page in train (`same_template_in_train` below). No two files are byte-identical, and the text differs (names, amounts, dates): the OCR-text trigram Jaccard never reached 0.8. pHash 8x8 over-states similarity for pages that are mostly white text blocks, so it was complemented by pixel correlation and text overlap.

| split version | slice | n pages | pHash<=4 to a train page | pixel NCC>=0.90 | NCC>=0.95 | text trigram Jaccard>=0.6 | same template in train |
|---|---|---|---|---|---|---|---|
| v2 issuer split | test / layout_ABC | 161 | 116 | 112 | 71 | 61 | 161 |
| v2 issuer split | test / layout_D | 174 | 3 | 3 | 0 | 58 | 0 |
| v2 issuer split | val / layout_ABC | 155 | 114 | 110 | 74 | 47 | 155 |
| v2.1 template-held-out | val / layout_ABC | 337 | 28 | 122 | 39 | 50 | 0 |
| v2.1 template-held-out | test / layout_D | 174 | 3 | 3 | 0 | 51 | 0 |

Affected in v2: all 11 generated types x layouts A/B/C (val 155, test 161 pages). Layout D (174 test pages) was never affected. v2.1 holds out whole templates (layout D = test; one rotating layout of A/B/C per type = val; the other two = train): `same_template_in_train` is 0 for every val/test page and no template spans splits. Residual similarity (NCC>=0.90 for ~36% of val pages) comes from different layouts sharing a white-page text-block look, and Jaccard>=0.6 from the generator's shared wording per document type - both cannot be removed by splitting.

**Second finding (older Task A/B synthetic data, NOT altered):** `synthetic_in` (2,430 project-generated bills) is split document-by-document from a single template family. Val: 227/243 pages are pHash<=4 from a train page (80 at distance 0); test: 233/243 (84 at distance 0); pixel NCC>=0.95: 177/243 val, 182/243 test (median text Jaccard ~0.5). These 243 test documents are inside the protected Task A, document_type and Task B test files (v2 had not flagged them; v2.1 now sets `in_protected_task_test` for 814 docs). The protected splits were **not** changed. Consequence: any Task A/B metric that includes these documents is optimistic; recomputing the metrics on the real-only subset is recommended (not done here - protected evaluation).

## 4. Label-mapping review

The three axes stay separate (document type / Task A expense category / derived tax-evidence candidates; no expense category equals a document type; eligibility is only `pending_verification` or `not_applicable`). Every real label except the `rvl_cdip` and `in_financial` source labels is a collection-rule mapping marked `needs_mapping_review` (5,052 rows); 78 of them contradict their own OCR text cues and are `flagged_for_review`. Known ambiguities: receipt vs invoice vs hotel/fuel/medical/travel (a hotel receipt can be `receipt` or `hotel_bill`), `in_financial` utility rows without a utility subtype, real `invoice` rows that mention rent, and EV/loan/school-fee/rental-agreement tax candidates (see `tax_mapping_note`). A human must resolve the queue before any label is called verified.

## 5. Baseline experiment (`reports/doc_type/experiments_v3/tfidf_baseline_v2_1.json`)

TF-IDF (char 2-5 + word 1-2) + logistic regression (C=10, balanced; fixed beforehand, nothing tuned), OCR text only, approved data only, generator watermark stripped. Task A model, V1 snapshot, frozen test and V2 annotation were not touched; the real test split was read **once** at the end (section 5.4).

| diagnostic | result |
|---|---|
| watermark kept vs stripped (macro-F1): real val / layout D / synthetic val | 0.7871 vs 0.7886 / 1.0 vs 1.0 / 1.0 vs 1.0 |
| real val docs predicted into synthetic-only classes: plain / with watermark appended / primary model | 0.0 / 0.0248 / 0.0 |
| class titles / key phrases masked (60 phrases): layout D / synthetic val / real val | 1.0 / 1.0 / 0.7926 (unmasked 1.0 / 1.0 / 0.7886) |
| all digits masked: real val / synthetic val / layout D | 0.8 / 1.0 / 1.0 |
| 1163 generator issuer names masked (layout D) | 1.0 (unmasked 1.0) |
| label-permutation control accuracy: real val / synthetic val (chance ~0.05) | 0.2946 / 0.0104 |
| source-only majority baseline accuracy: real val / synthetic val / layout D | 0.6782 / 0.1818 / 0.069 |
| seen-layout (issuer-grouped) vs unseen layout D, synthgen-only model, accuracy | 1.0 vs 1.0 |
| watermark-like features in the top-20 word features per class | none (one OCR-merged fragment 'cashier syntheticsample' in school_fee_receipt in the first run; stripping now tolerates OCR-dropped spaces) |
| documents with watermark residue after stripping | 13 (11 OCR-garbled footers, 2 genuine 'synthetic' words in real rvl_cdip docs) |

Reading: the watermark, class titles, digits and issuer names are **not** what makes the synthetic slices easy; the synthetic classes differ from each other in ordinary vocabulary (landlord/tenant, lessor/lessee, EMI/borrower, kWh/charging...), which is by construction of the generator. The synthetic score therefore measures consistency with the generator's own wording, not robustness. Cross-domain transfer is poor in both directions: a real-only model scores accuracy 0.0026 on synthetic val (it has never seen those classes) and a synthetic-only model 0.2376 on real val (it labels most real receipts `invoice`). Adding the synthetic data to the real training set did **not** help the real classes (real val macro-F1 0.8019 real-only vs 0.7886 combined).

### 5.4 Real test split, read once (frozen configuration, no feedback)

n=399 approved real test documents (the protected test split minus excluded sources). real-only: accuracy 0.9273, macro-F1 0.784; combined: accuracy 0.9148, macro-F1 0.7729 (8 classes; `medical_bill` has 1 test doc). Consistent with validation; no decision was based on it.

### 5.5 What this does and does not support

- Supported: for the 8 real-backed classes a simple OCR-text model reaches ~0.91-0.93 accuracy, macro-F1 ~0.78-0.80 on 404 real val docs; small classes (medical_bill n=2, fuel_receipt n=13, utility_bill n=21) are too small for reliable per-class numbers; 100 Indian val docs: accuracy 0.94.
- **Not supported:** any real-world claim for the 12 classes without approved real documents - the EV, meal voucher, rent receipt, rental agreement, school fee, insurance (80C/80D), investment (80C), loan interest, loan statement classes plus salary slip, form 16 and bank statement - which have synthetic-only train/val/test.

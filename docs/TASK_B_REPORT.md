# Task B report: field extraction / document understanding

> **Task B is a research prototype, not a production OCR service.** Generated by `scripts/taskB/make_report.py` from `reports/taskB/*.json` and `models/taskB/hybrid.json`. Real-document results are the headline; synthetic results are always reported separately and are **not** evidence of real-world generalisation.

## 1. Objective
Input: one bill page (image or PDF page), its OCR words and bounding boxes. Output: structured JSON with, per field, value, calibrated confidence (null when no calibrated score exists), model score, source system and bbox. A field the document does not contain is **omitted (null)**; nothing is guessed. Task A (classification) is untouched; Task B reuses its manifest, OCR annotations, group-based splits and image conventions.

## 2. Canonical schema
34 fields in six groups (`models/taskB/field_schema.json`): universal (merchant_name, merchant_address, invoice_number, invoice_date, subtotal, tax_total, total_amount, currency, payment_method); Indian tax (gstin, cgst, sgst, igst, hsn_sac); employee (employee_name, employee_id); travel (origin, destination, travel_date, pnr, ticket_number, passenger_name, flight_number, train_number, bus_number, vehicle_number); hotel (check_in, check_out, room_number, number_of_nights); medical (patient_name, prescription_number, pharmacy_name, doctor_name). Normalisation (`schema.py`): amounts -> float (default `1,234.50`, EU `6,14`, Indonesian thousands-only); dates -> ISO; GSTIN -> 15-char pattern (+ checksum helper, OCR digit/letter repair); ids/text -> alnum-casefold; places -> city part. Source -> canonical mapping and unsupported source fields: `reports/taskB/schema_mapping.md`.

## 3. Dataset composition
Task B documents: **6442**; **real 2932**, **synthetic 3510**, Indian real 285. Splits (existing group-based manifest split, unchanged): {'train': 5160, 'validation': 646, 'test': 636}; `synthetic_b` (1,080 Task-B-only synthetic bills for fields no real data annotates) uses a seeded document-level split. Sources: {'sroie': 958, 'cord': 998, 'receiptbench': 867, 'invoices_pt': 109, 'synthetic_in': 2430, 'synthetic_b': 1080}. A field is scored on a document only if its source annotates it (absence is then meaningful).

**Ground-truth correction applied once, to all splits, before the final numbers below.** ReceiptBench stores `std_total = '0.00'` as a placeholder when unknown while `orig_total` holds the printed total. The first mapping read only `std_total`, so 182 documents (27 in the real test set) were scored against a wrong zero. Now `total_amount` uses `std_total`, else `orig_total`; 88 totals were recovered, 94 documents with neither are **not scored** for total_amount. No other label or split was changed. Effect on the same models: real micro-F1 hybrid 0.652 -> 0.663, LayoutLMv3 0.632 -> 0.646 (`final_results_before_gt_fix.json` keeps the old run). The candidate ranker was retrained on corrected labels (cheap); LayoutLMv3 was **not** retrained (its token labels differed only on those documents, mostly missing rather than wrong).

## 5. Baseline (deterministic)
Regex + keyword + position heuristics over OCR words/boxes (`baseline.py`): no learning, no per-dataset tuning, generic bill vocabulary only, crude locale/currency inference, year-like numbers excluded from amounts. Its hotel/travel/medical/employee patterns use label words that the `synthetic_b` templates share, so its synthetic scores are optimistic.

## 6. Candidate ranker
Candidate generation (amounts, dates, 15-char tokens, id-like tokens and 2-3 word windows, text lines/':' suffixes/line windows) + one gradient-boosted classifier per field (value, position, line shape, hashed left/previous/next-line context); CPU only. Decision = best candidate per field, abstain below the field threshold; confidence = isotonic calibration.

## 7. LayoutLMv3
`microsoft/layoutlmv3-base` token classification, BIO tags for all 34 fields over OCR words + boxes + page image; 384-subtoken sliding windows (stride 96); micro-batch 2 x accumulation 8, bf16, up to 5 epochs with early stopping on validation token-F1 (RTX 4050, 6 GB, ~45 min). Training log: {epoch: 1, train_loss: 0.4901, val_token_f1: 0.9432, sec: 536}; {epoch: 2, train_loss: 0.0517, val_token_f1: 0.9475, sec: 1074}; {epoch: 3, train_loss: 0.0306, val_token_f1: 0.9647, sec: 1607}; {epoch: 4, train_loss: 0.0205, val_token_f1: 0.9663, sec: 2137}; {epoch: 5, train_loss: 0.0135, val_token_f1: 0.9661, sec: 2666}. Decoding: contiguous B-/I- spans plus a best-B fallback; value normalised per field. Weights are CC-BY-NC-SA-4.0 (non-commercial).

## 8. Final system
**Hybrid + applicability gating.** Per field, one system (LayoutLMv3 / ranker / baseline) is used. Choice and thresholds follow a fixed policy that never touches the test set:

* A field's score threshold and system are **tuned on REAL validation documents only if >= 30 real validation documents carry a GT value for it**; otherwise a fixed untuned default is used (threshold 0.5, system `layoutlm` = best real-validation micro-F1 over the well-supported fields: layoutlm 0.678, ranker 0.613, baseline 0.484) and the field is flagged **LOW-SUPPORT**.
* Confidence = isotonic regression of 'prediction correct' on the model score, fit on real validation predictions when >= 30 exist (else all validation predictions, flagged).
* Gating (`gating.py`): hotel/travel/medical/employee/HSN/tax-part fields are emitted only if the document text contains evidence words. `tax_total` is derived from IGST only for IGST-only bills (annotation convention); `currency` comes from the baseline (symbol rules).

## 9. Evaluation methodology
Same held-out test set for every system (`final_eval.py`; test is scored once per system, never used for tuning). Per field: support (docs with GT), precision, recall, F1 with TP = predicted and equal to GT, FP = predicted and (different or GT absent), FN = GT present and (missing or different). **Normalised match**: amounts within 0.005, ISO dates, normalised GSTIN, alnum-casefold text/ids; **soft match** for text/place (0.9 similarity or containment) reported separately; **exact raw match** = raw OCR string equals raw GT string (text/id/GSTIN fields only; amounts/dates have no meaningful raw form). **Null rate** = share of scored documents with no prediction; **hallucination rate** = share of documents where the field is annotated as absent but a value was emitted. Micro-F1 pools TP/FP/FN over fields; macro-F1 averages per-field F1 for fields with >= 5 GT documents. Intervals: grouped bootstrap over real test documents (400 resamples; groups = near-duplicate/template families).

## 15. Limitations
* Real Indian field annotation comes from one source (ReceiptBench); real Indian GSTIN/CGST/SGST test support is 4-13 documents; HSN/SAC and IGST have effectively no real evidence; subtotal/address/tax_total have none for Indian bills.
* Many errors stem from OCR/annotation mismatch (GT value not locatable on the page), so the achievable ceiling on real data is below 1.0 even for a perfect model.
* Confidence is unreliable on Indian documents (small calibration set).
* The ranker and baseline cannot read a value the candidate generator never produces; LayoutLMv3 was trained for ~45 minutes on 5k documents, 3k of them synthetic, and was not retrained after the ReceiptBench total correction.
* Locale/date-order and `$` currency ambiguity are heuristic.
* ReceiptBench annotations are incomplete in places (combined GST lines, placeholder zeros, city-level travel fields), so some counted false positives are correct extractions and some counted misses are annotation gaps; per-field numbers are therefore conservative for those fields.
* The synthetic_b templates reuse the Task A renderer: synthetic-only fields are unproven on real bills.

## 16. Final recommendation
* **Final system: the hybrid (LayoutLMv3 for most fields, ranker for subtotal/travel_date, baseline for currency) with the documented real-validation threshold policy and applicability gating.** Selection used real validation only; on the held-out real test it is also the best system (real micro-F1 0.663 vs LayoutLMv3 0.646, ranker 0.546, baseline 0.444).
* **LayoutLMv3 genuinely improves over the ranker and the baseline on real documents** (paired bootstrap, section 10), by roughly 10 and 20 F1 points.
* **Verdict: research prototype, not production-worthy.** Real micro-F1 is ~0.66 (macro ~0.58); merchant name (F1 ~0.54) and invoice number (~0.42) are unreliable; Indian GST fields are supported by tens of documents from one source; confidence is not trustworthy enough on Indian bills for auto-approval.
* **Most valuable next steps:** annotate ~100-200 real Indian GST invoices/receipts (GSTIN, CGST/SGST/IGST, HSN/SAC, invoice number, subtotal, tax total, address); retrain LayoutLMv3 on the corrected labels with more real data; add OCR-error-aware matching; re-fit calibration on real Indian validation data before routing decisions.
